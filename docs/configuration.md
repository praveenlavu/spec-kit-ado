# Configuration: `ado.config.json`

The `ado` CLI and the `speckit.ado.*` commands read `ado.config.json` from the current
directory, or from the path in `$ADO_CONFIG` when that is set. The file holds names and
settings only, never a token, and is meant to be committed. A full example with every
key at its default, except `story_type`, `done_state` and `removed_state`, is in
[ado-config.template.json](../ado-config.template.json). Those three are left out on purpose: they are the
keys `ado setup` detects from your project, and it fills in only keys that are absent, so a copy of the template
lets detection run on any process template (a key you copy in would be kept as is, even if wrong for your project).
Without them the defaults apply: `User Story`, `Done` and `Removed`, which fit Scrum's Done but not Agile's `Closed`.

`ado setup` writes `organization` and `project` and keeps every other key already in the
file. With the verified PAT it also looks up the project's requirement type
(`workitemtypecategories/Microsoft.RequirementCategory`) and that type's `Completed` and
`Removed` states, and writes `story_type`, `done_state` and `removed_state` for any of
the three not already set (Agile gives `User Story` / `Closed` / `Removed`; Scrum gives
`Product Backlog Item` / `Done` / `Removed`). If the story type and the Task type
disagree on the Completed state, it asks you to pick one. If a lookup fails it prints a
one-line note and leaves the defaults. It also appends `.ado/` to `.gitignore` beside the
config, unless the line is already there. If the file exists but is not a JSON object, `ado setup` refuses to overwrite it
and exits 2. `speckit.ado.setup` adds `stack` after you confirm the phase map.

### Profiles: `ado setup --profile`

`ado setup --profile starter|team|strict` also writes the keys of one profile, and only these:

| Profile | Keys written |
|---|---|
| `starter` | `"mode": "advisory"` |
| `team` | `"mode": "advisory"`, `"gate": {"block": ["ac_traceability", "open_questions"]}`, `"review_block_on": ["blocker"]` |
| `strict` | `"mode": "strict"`, `"strict": {"test_command": "<your test command>"}` |

`team` repeats `starter`'s `mode`, but `strict` does not repeat `team`'s two lists: strict mode adds `ac_traceability`, `open_questions`
and `blocker` to the effective `gate.block` and `review_block_on` itself (the strict floor), so the effective config is the same as
if they were written, and a config that already has the team lists keeps them.

`strict.test_command` is left alone when `ado.stack.json` is approved (`ado stack approve --apply` writes it) or when the config
already has one; otherwise setup asks for it, and a blank answer leaves it unset. Setup never removes a key; a list it sets
(`gate.block`, `review_block_on`) keeps the entries you already have and adds the missing ones. On an existing config it prints
each change as `key: old -> new` (`(not set)` for a new key; `key: changed` when a value is over 80 characters or looks like a
secret) and writes only after a `y` typed in a terminal: any other answer, or no terminal, writes nothing and exits 2. Without
`--profile`, setup behaves as before. The config is checked with the same validator as `load` before anything is stored, written
atomically (temp file in the same directory, `os.replace`) and read back, keeping its indent and line endings; a symlinked config is
refused. The `team` and `strict` profiles also ask for `approvers` (optional: identity GUIDs separated by commas or spaces, blank to skip; a skipped
question writes nothing, an `approvers` already in the file is kept and not asked again, a bad entry is refused by position before anything is
stored). See [Approvers and comment mode](#approvers-and-comment-mode-the-recommended-setup), the [quickstart](quickstart.md)
and the [glossary](glossary.md).

## Keys

Every string in the file, values and object keys at any depth, must be free of control characters (C0, DEL, C1, U+2028/2029, surrogates, private use, and invisible format characters such as bidi overrides, BOM and soft hyphen; the joiner and direction marks U+200C-U+200F are allowed); otherwise `Config.load` fails with `ConfigInvalid` naming the key (exit 3 in CI), and `ado setup` refuses to write such a value, because the file comes from the PR itself and could otherwise inject lines into CI logs.

**In CI the config is untrusted.** The gate and the branch guard read `ado.config.json` (and the ledger) from the PR's own checkout, so the PR's author controls every key, including `gate.block` and `branch_prefix`. That is why an invalid file fails the gate closed (exit 3) rather than being skipped, why control characters are rejected, and why anything CI echoes from it is cut to one line with control characters replaced by spaces. Protect the file with `CODEOWNERS` and branch protection if `gate.block` matters to you (see the CI docs' trust model).

|---|---|---|---|

The other commands read it as before. |
| `gate` | object | `{"tests": {}, "block": []}` | Gate settings, below. A partial object keeps the defaults for missing keys. |
| `attachments_allow` | list of strings | `[".md", ".svg", ".txt"]` | File extensions, each with its leading dot and compared case-insensitively, that `ado attach` and `ado done` may upload (anything else aborts) and `ado attachments --download` may save (anything else is listed as skipped). |

| `removed_state` | string | `"Removed"` | The project's Removed-category state (`ado setup` detects it). |
| `active_state` | string | `"Active"` | State `speckit.ado.pull` offers to move the story to. Read by that command from the file, not validated by the CLI. |
| `task_type` | string | `"Task"` | Work item type `ado push` creates under the story. A work item type of the project (not validated). |
| `repo_host` | `"github"` or `"azure"` | `"github"` | Where PRs are opened: `gh` for GitHub, the ADO REST API for Azure Repos. Only `"azure"` selects Azure Repos; any other value behaves as GitHub. `ado pr comment` and `ado branch <id> --link` work only with `azure`. |
| `repository` | string | `""` | Azure Repos repository name. Required when `repo_host` is `azure`. |
| `branch_prefix` | string | `"feature/"` | Start of the feature branch name: `ado branch <id>` names it `<branch_prefix>ab<id>-<slug>` (e.g. `feature/ab1001-count-active-members`), and `<branch_prefix>ab<n>` at the start of a branch name ties it to story `<n>` (as does `AB#<n>` anywhere). A plain `<branch_prefix><n>-…` does not: Spec Kit's own `001-…` / `20261028-143022-…` branches never read as a story, whatever the prefix. May be empty; otherwise letters, digits, `.`, `_`, `-`, `/` starting with a letter or digit, with no `..`, `//`, `/.` or `.lock/`. |
| `mode` | `"advisory"` or `"strict"` | `"advisory"` | `"advisory"` keeps every v0.2 behaviour. `"strict"` turns on strict SDD+TDD: the effective `gate.block` and `review_block_on` are your lists plus the strict floor (`gate.block` gains `ac_traceability`, `assertion`, `open_questions`, `commits_without_story`; `review_block_on` gains `blocker`), with your entries kept first and no duplicates. | `rules` | object | `{"enabled": false, "types": ["Epic", "Feature"]}` | Business-rules settings; a partial object keeps the defaults. `rules.enabled`: a boolean, `false` leaves every output exactly as without the key; `true` makes `ado dod` walk the ancestors and write the ledger header line `Rules from:`. `rules.types`: a list of 1-10 non-empty strings of at most 64 characters, the work item types whose Description may carry a `Business rules` section; it may not contain `story_type` (compared case-insensitively). An unknown key (reported by position, never echoed), a value of the wrong type or length, or a `rules` that is not an object is a config error (exit 2; `ado gate` exits 3). With `enabled: true` `ado gate` also runs the `rule_coverage` check and adds a `rules` key to its JSON (see [business-rules-reference.md](business-rules-reference.md#the-gate-check)) and the online `rule_drift` check (see [Drift](business-rules-reference.md#drift)). With `mode: "strict"` the `pr` and `done` phases of `ado strict check` (and so `ado pr create` and `ado done`) also run the offline rules check and refuse with `rule-uncovered`, `rule-unknown`, `rule-unconfirmed`, `rule-changed`, `rules-problem`, `rules-missing`, `rules-format` or `rules-header`, which no override can waive; a rejected `out of scope:` decision is then no `decision-rejected` finding and no `open_decisions` entry, because the rule it tried to lift is back in scope (see [Strict mode](business-rules-reference.md#strict-mode)). In strict CI the config comes from the target branch, so a PR cannot switch rules off. |
| `stack` | object | `{"kit": "", "phases": {}}` | Phase map for routing; see [stack-kits.md](stack-kits.md). |
| `approvers` | list of strings | `[]` | Who may approve in comment mode: 0 to 20 ADO identity ids (GUIDs, any case, stored lowercase). An entry that is not a GUID, the anonymous identity (all `a`), a 21st entry, or a duplicate is a config error naming the entry by position (a duplicate is rejected, not collapsed). **Read only from the target branch**: see [Approvers and comment mode](#approvers-and-comment-mode-the-recommended-setup). |
| `approval` | `"terminal"` or `"comment"` | `"terminal"` | How gates and verdicts are approved. `"terminal"` is today's behaviour; `"comment"` asks for an approver's comment on the story. Read only from the target branch. |
| `unattended` | object | `{"assume_after_hours": null, "approval_requests": false}` | Settings for runs with nobody at a terminal; a partial object keeps the defaults. `assume_after_hours`: an integer from 1 to 720 (no `null` in the file: leave the key out). `approval_requests`: a boolean, `false` unless you turn it on (owner ruling: the kit posts no approval-request comments by default). An unknown key is reported by position. Read only from the target branch. |

**`strict.test_command` and the stack profile.** Once a project has an approved stack profile (`ado.stack.json`), `strict.test_command` comes only from `ado stack approve --apply` (`ado setup --profile strict` leaves it alone then, and asks for one only while no profile is approved): it writes the command composed from the approved stacks, or removes the key when no stack defines a test command, and re-approving is how to change it (the profile's `strict.test_command` must equal the composed command; a hand edit is drift, and so is any `strict.test_command` at all when no stack defines a test command). `ado setup` and `speckit.ado.setup` never write it. Hand edits are for projects without a profile. `approve` rewrites `ado.config.json` keeping the parsed value and key order of every other key (indent, line terminator and trailing newline are kept; spacing may change), refuses when `ADO_CONFIG` is set (`Config.load` would read that file instead) or when the file is invalid, symlinked or not a regular file, and needs a terminal (a guard against accidents, not a security boundary).

A minimal strict config is `{"mode": "strict", "strict": {"test_command": "python3 -m pytest -q", "test_timeout": 300}}`. The test command runs with the PATH of the environment that runs the check (put the toolkit venv first if your tests need it): a Mac has no `python`, so use `python3`. In strict mode set `close-story: true`: without it no strict `done` runs (it is the CI link-on-merge input; `closeStory` on Azure Pipelines).

In strict mode `ado pr create`, `ado done` and `ado gate` use the effective lists (`gate.block` plus the floor, `review_block_on` plus `blocker`), and `pr create` and `done` run the `pr` and `done` strict check first (exit 2, nothing sent). With `mode: "strict"`, `ado strict check <id> --phase implement|pr|done` (optional `--base REF`, `--head REF`) applies the strict rules (see the README's Strict mode section); the `implement` phase refuses while `strict.test_command` is unset, and the `pr` and `done` phases check the red/green commit evidence in ledger section 3 (L1; test files are the `gate.tests` globs plus the built-in ones; a red commit may also change only the story's `DoD_<id>.md` and `Decisions_<id>.md` in `dod_path` and the spec dir's `tasks.md`). L1 reads git history, so CI must use a full clone (`fetch-depth: 0`). `ado strict override <id> <rule> --reason "<text>"` (a human, in a terminal; not a security boundary) records an override that lets one of `test-command`, `l2`, `open-question` or `placeholder` pass for the story (never a business-rules finding). `ado strict verify <id>` runs `strict.test_command` at each AC's red commit (must exit non-zero) and green commit (must exit 0) and at `HEAD` (must exit 0), each run limited to `strict.test_timeout` seconds, and records the result in ledger section 4; `ado strict check` then validates that record (`record-missing`, `record-stale`, `record-incomplete`, `record-failed`, `record-command-mismatch`) without running anything. **`strict.test_command` is code from your project**: the test runner executes it at one commit in a temporary checkout (a throwaway `git clone --shared --no-checkout` outside the repo, no shared config, hooks or index), with a scrubbed environment for the command and for every git call (an allow-list: no `GIT_*`, `ADO_TOKEN`, `GH_TOKEN`, `*_TOKEN`, `*_PAT`, `*_SECRET`, `*_KEY`, `*_PASSWORD`, `AWS_*`, an empty temporary `HOME`), no stdin, a timeout of `strict.test_timeout` seconds and no output returned. It is hygiene, not a sandbox: the command keeps your user's filesystem and network access, can read and change its own checkout's `.git`, and a process that calls `setsid` escapes the timeout kill. **Not a sandbox, in detail:** the environment allow-list passes only `PATH`, `LANG`, `LC_*` (the 13 standard POSIX locale names only), `TERM`, `TMPDIR`, `VIRTUAL_ENV`, `JAVA_HOME`, `GOPATH`, `NODE_PATH` and the SDK locations `GOROOT`, `FLUTTER_ROOT`, `DOTNET_ROOT`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `RUSTUP_HOME` (these six only when set to an absolute path without control characters); `CARGO_HOME`, `GRADLE_USER_HOME`, `PUB_CACHE` and every `SF_*`, `SFDX_*` and `SALESFORCE_*` variable are never passed, and the deny pass for `*_TOKEN`, `*_KEY`, `*_SECRET`, `*_PASSWORD` still runs after the allow-list. An empty temporary `HOME` hides default lookups only: a hostile test command can still read credential directories by absolute path, such as `~/.sfdx`, `~/.sf`, `~/.npmrc`, `~/.cargo` or `~/.config/gh`. The `--shared` clone's `.git/objects/info/alternates` names the original checkout, so the command can find it and read its `.git/config`; keep `persist-credentials: false` on every checkout (the shipped workflows and pipelines do) so that file holds no token. This is process hygiene, not a sandbox. Global and system git config are ignored, so Git LFS filters do not run and LFS files are checked out as pointer files. CI must run it without secrets: check out with `persist-credentials: false` (the shipped workflows do) and run the test command in a job where no step holds secrets. `l2` also covers `test-command`, so one `l2` override lets an unset `strict.test_command` pass. `ado strict verify` honours overrides like `check`: with an `l2` or `test-command` override in force it runs no tests, records nothing and exits 0 with `verification skipped: overridden` (and `overrides_used`) (with `--no-record`, as in CI, an override in force is instead the finding `override-in-force` and exit 2 unless `--allow-override` is passed).

### CI trust: the config comes from the target branch

In CI the PR controls the files it is judged by, so `ado gate --base REF`, `ado strict check --base REF`, `ado strict verify --base REF` and `ado branch --id-from NAME --base REF` (both CI templates pass `--base origin/<target branch>` to the gate and the story-id step, and ask `ado strict mode --base origin/<target branch>` first) read `ado.config.json` from the **target branch** first, with `git show` at the full ref (`refs/remotes/REF`, then `refs/heads/REF`, then a full 40-hex commit id; never a tag, a short name or an option-like value). If that file exists and says `mode: "strict"`, the **whole config is the target's**: `gate.block`, `gate.tests`, `dod_path`, `branch_prefix`, `review_block_on`, `strict.test_command`, `strict.test_timeout` and the rest; the gate's commit range is also walked from the resolved commit id, so a tag named like the base cannot move it. The PR's own `ado.config.json` is not read, so a PR cannot lower `gate.block`, set `mode` to `advisory`, point `strict.test_command` at `true` or make every file a test with `gate.tests: {"**": ...}`. The `gate` summary or PR comment then carries one extra line, `config: target branch (strict)` (JSON key `config`); when `--base` is given and the PR's own config is strict, it says `config: pull request`; with an advisory config nothing is added.

- The target has **no** `ado.config.json`, or says `advisory` (or no `mode`): the PR's config applies, exactly as in v0.2, and a PR that adds strictness is judged by it. The first PR that introduces strict mode is therefore judged by its own config (the target has none yet); from its merge on, the target's config applies.
- The target's file is unreadable, invalid (the same checks as above, nesting too deep included), larger than 1 MiB, not a regular file, or git fails: `ado gate` and `ado branch --id-from` exit **3**, so CI fails closed (`strict check` and `strict verify` exit 2, an `error:` line and no JSON). The message never echoes the ref or the file's text.
- REF is no commit in the checkout (a shallow clone: use `fetch-depth: 0`; or `origin/main` in a repo with no origin): the target cannot be read. If the PR's own config is **strict** (or invalid) that fails closed as above (exit 3 for `gate`, 2 for the strict verbs). If it is advisory or has no `mode`, the v0.2 path applies unchanged: the gate notes that commits were not checked and does not block on it.
- **Recovery from exit 3.** To recover from exit 3 on an invalid target-branch config, fix the target config through an admin-bypass merge, or run the gate once without `--base`. A PR that fixes the config cannot pass the gate on its own, because the gate reads the config of the target branch, which is the invalid one; this holds in an advisory repo too.
- Without `--base` nothing changes: the working tree's config is used.
- **Only the repo-root `ado.config.json` is trusted.** With a non-default `config-path` (GitHub) or `ADO_CONFIG`, the target's root file is what is read; if the target has none, the PR's config applies silently.
- **Protect what judges the PR** on the target branch with branch protection rules and `CODEOWNERS` (required review from code owners): `ado.config.json`, and the CI definition itself, which is PR-controlled too (the GitHub caller workflow and its `toolkit-ref`; the Azure PR pipeline YAML). The ledger and decisions file are still the PR's own files; the strict checks read them but judge them with the target's rules.
- **What the shipped templates now enforce, and what is still yours.** Under a strict target they fail (not skip) when the PR has no story id, run `ado strict check <id> --phase pr --head <head sha> --base origin/<target>` after the gate (no token; rule ids only in the comment) and fail on it, and the link-on-merge templates fail when the strict `done` check refuses. Protecting the workflow or pipeline files, the caller workflow and `toolkit-ref`, and `ado.config.json` stays your job (branch rules or `CODEOWNERS`); the Actions and Azure agents have not been run in this project's environment, so the template logic is covered by `bash -n` and real-bash tests with a fake `ado` only.

`organization` and `project` must be present and non-empty, `story_type` and
`removed_state` and `done_state` must be non-empty strings when set, `gate`, `stack`, `strict` and `rules` must be
objects (so must `unattended`), `approvers` a list of at most 20 GUIDs, `approval` `terminal` or `comment`, `mode` must be `advisory` or `strict`, `attachments_allow` must be a list of strings, `branch_prefix` must be
git-ref-safe as above, `gate.block` entries must be known check names (`ac_traceability`,
`assertion`, `ac_drift`, `open_questions`, `commits_without_story`, `open_decisions`, `rule_coverage`, `rule_drift`) and `review_block_on` entries
must be `blocker`, `major` or `minor`; otherwise the CLI exits 2
with a message naming the problem.

An invalid config file (present but failing any check above) is explicit misconfiguration, not
missing information, so `ado gate` and `ado branch --id-from` exit **3** instead of 2 (every other
verb keeps 2). The CI gates fail on an invalid config: GitHub posts `ADO gate FAILED:
ado.config.json is invalid: <message>` as the PR comment and turns the check red; Azure Pipelines fails
the build with an error annotation carrying the first line of the CLI message and posts no PR thread
(`ado pr comment` needs the same config); the workflow's `gate-check` halts on exit 3. A missing config
file or token stays exit 2 and advisory.

### Approvers and comment mode: the recommended setup

`approvers`, `approval` and `unattended` decide who may approve things, so they are a trust boundary. They are read **only from the target
branch** (`origin/HEAD` locally, `--base` in CI). The reader for the verbs is `config.trusted(repo, base)`, which returns only the three
keys (`Trust(approvers, approval, unattended)`); `ado doctor` reads the same target-branch file through its own code (`Config.load_from_ref`),
never the working tree that a pull request edits: a PR that adds an approver, switches `approval` or sets `unattended` changes nothing until it is merged. A target branch with
no `ado.config.json` means the defaults (no approvers, `terminal`). An unreadable or invalid target config, or a base that is no commit
here, refuses (`ConfigInvalid`, exit 3 where that already applies) instead of falling back. `config.trusted` also refuses a base that is not a
plain ref name (a revision expression such as `main@{1}` or `origin/main~1`, a range, a space, a `:` or a leading dash), since it could pick an
older target config. With **no** base at all (a fresh repository without
`origin/HEAD`) the defaults apply while the working-tree config (found as `Config.load` finds it, a symlink to a regular file included, and the
file `$ADO_CONFIG` names) sets none of the three keys, exactly as before; if it sets any of them, or is over 1 MiB or not a JSON object, the answer is
a refusal, "set origin/HEAD or pass --base", because the keys cannot be checked against anything. The refusal texts are fixed and name no file. Absent keys change no
output of any verb.

In this build the keys are validated, `trusted` reads them, `ado doctor` checks them and `ado setup --profile team|strict` asks for the
approvers. The code that decides which comment counts exists (`ado.approvals`, below). Two verbs use it so far, `ado decisions <id> --sync` and `ado questions <id> --sync` (below); `ado approvals`, the other sync verbs and
the applies in comment mode come with the later tasks of this version: until they ship, setting `approval` changes no behaviour other than the doctor row, and with `approvers` set `ado decisions --resolve` is refused.

**Which comment counts (`ado.approvals`).** An approver approves by posting a comment whose **first non-empty line is the whole command**:
`/approve D<n>` or `/reject D<n>: note` for a decision, `/answer Q<n>: text` for a question, `/approve <gate-id> <64 lowercase hex>` or
`/reject <gate-id> <hash>: note` for a gate (a gate needs the hash, a decision or question must not carry one). Notes are cut to 300 characters,
answers to 500, and both are scrubbed (addresses, mentions, control and invisible characters): a long `/reject` note is capped, never refused, so it still retracts an earlier approval. Quoted text is cut out
before the line is read (`<blockquote>`, `<q>` and any element whose `class` contains `quote`, such as a mail client's reply markup), so quoting a request
and replying under it works, while a quoted `/approve` never counts; a command on the second line never counts either, and neither does one behind a first line that merely starts with `>`. A first line that looks like a command but breaks the grammar (`/REJECT D3`, `/reject D3 reason` with no colon, a hash that is not 64 lowercase hex) is a bad line: it is counted, never shown, and when an approver wrote it after the newest valid comment for that target (a line is skipped only when it names a different well-formed target; `/reject D3.`, `/reject (D3)` and `/reject D03` count for D3, and so does a retraction over the 16 KiB read limit) the reader returns that count as `bad_newer`, which the verbs must show next to the verdict (a retraction typed wrong would otherwise leave the earlier approval standing silently). A comment counts only if all
of these hold, and the first one that fails is counted by name, never shown: `on-behalf` (it carries `createdOnBehalfOf`, which is what a work item
update written with `bypassRules` and a forged `System.ChangedBy` leaves behind: the comment's own author stays the real actor), `excluded-author`
(the token identity, the author of a `[spec-kit-ado:` comment, and the CI token identity once the verbs that know it pass it in), `not-approver`
(its author is not in `approvers`; ids are compared lowercase), `edited` (its version is not 1, unless its author made the edit and the text is
identical in every version and the listed versions are exactly 1 to n; an unreadable versions list counts as edited) and `forged` (the revision written with the comment says another identity
authenticated the write; this is defence in depth only, the `System.AuthorizedAs` field is real but whether a comment's time always equals its
revision's time is not verified, so "cannot tell" is not "genuine"). Of the valid comments for a target the newest wins by (created time, id): a later
invalid comment never cancels an earlier valid approval, a later valid `/reject` does. Comment mode is **refused** (exit 2, a fixed text) while the
token identity holds the "Bypass rules on work item updates" permission, **or when that cannot be read** (a restricted PAT may not read it): the
permission is what lets a token write a comment that looks like someone else's. Nothing proves yet that another user cannot edit or delete an
approver's comment (not tested with a second user); an edited comment does not count and a deleted one is missing, so deleting a `/reject` is a residual.
A quote is recognised by its HTML tags only: markup that a person's reply copies in from a comment the agent wrote is trusted to be neutralised by ADO's own editor
and sanitiser (the reader fails closed on unclosed quotes, on raw-text elements inside one, on a closing tag a browser would not read as one such as `</ blockquote>` or `</blockquote-x>`, on a nested `<blockquote/>` and on any `<!` token inside a quote; a first line made only of zero-width characters is a bad line; it is not a sanitiser), which was not verified. Anything after the first
16 KiB of a comment (once quotes are cut) is not read, and `ado comments` still converts a whole comment to text, which is slow on a megabyte of blanks.

**Approval flow for decisions: `ado decisions <id> --sync`.** With `approvers` on the target branch, the PO or another approver answers a posted decision in the story's comments: `/approve D3` or `/reject D3: reason` as the first non-empty line. Anyone (the agent included) then runs `ado decisions <id> --sync`, which writes the verdict into `Decisions_<id>.md` exactly as `--resolve` would (`→ validated|rejected · by: approver · note: … · via: <comment id>`; `via` is a decimal comment id and is validated like every other key). It is a **local write only**: it reads the comments (GET) and changes no ADO state, so it has no preview and no gate; only the target lines change, the rest of the file stays byte for byte (line endings included), and the write is atomic and read back. A verdict counts only when (1) the line's current text is the posted text: its `posted: <comment id>:<hash8>` marker matches the line now (else `edited`; no marker is `not-posted`), and the comment the marker names exists, starts with `[spec-kit-ado:decisions]`, was written by a kit identity and holds the line as it reads now (`posting-missing`, `posting-mismatch`: the marker is a claim in a file a pull request controls, so it is checked against the comment), is **unedited** (`posting-edited`: the same rule as for an approver's comment, version 1, or edited by its author with identical text in every version; the agent can rewrite its own comment, and an approval of the old words must not validate the new ones) and shows the line exactly (`posting-lossy`: a line cut at 500 characters, or with an address, mention or control character replaced, matches too loosely, so shorten or re-word it; with `approvers` set it cannot be resolved otherwise) and is plain text (`posting-markup`: the comment's raw HTML may hold nothing but the kit's own `<br>` line breaks, and only the pieces between `<br>` count as lines, a piece that breaks into two lines by itself (`&#10;`, a raw newline) is no line, so a decision hidden in a `display:none` span, a style or a script, which the PO would not see, is never matched; this is the rule `ado questions --sync` applies to the questions comment (`comments.kit_lines`). It fails closed: if ADO ever wraps the stored text of a comment in a `<div>` or `<p>`, the sync stops applying verdicts until the rule is relaxed, and the live check of P4-19 asserts that a real posted decisions comment passes); (2) the newest valid command for that decision (the guards above) is newer than the posting comment (and than its last modification, for an identical re-edit), by created time then comment id and never by the local clock (`older-than-posting`: an approval given before the text was posted again, or before it was reworded, does not count); (3) the line is open, or was itself written by a sync (it has `via`): a verdict a human wrote in a terminal is `resolved-locally` and never overwritten, and a line a sync resolved is `up-to-date` when the newest valid command says the same and its `via` is that comment (a hand-written `via` that names another comment is replaced by the verified one; with no valid command it is left alone). An approver's later valid `/reject` therefore overrides an earlier synced `/approve` (the line is rewritten with `via` of the newer comment), and a later `/approve` an earlier synced `/reject`; a later comment that is edited, quoted, by the agent or by a non-approver counts for nothing. The note is the command's note scrubbed again (addresses and mentions replaced, control characters, `<!--`, `-->`, code fences, `·`, `→` and `->` removed) and capped at 300 characters; if even that would not read back, the verdict is written without a note; a line that still cannot be rewritten (an inline `<!-- -->`, over 2000 characters) is `unwritable` and listed. The output (JSON) lists `applied`, `skipped` (id → rule: `not-posted`, `edited`, `posting-lossy`, `posting-missing`, `posting-mismatch`, `posting-markup`, `posting-edited`, `resolved-locally`, `no-verdict`, `older-than-posting`, `bad-comment-id`, `up-to-date`, `unwritable`), `status` and `bad_newer`, the count of later malformed command lines by an approver for each checked decision (fixed text, a number only: `/reject D3.` may be a retraction typed wrong, so read the thread when it is not 0). It **refuses** (exit 2, a fixed text naming only decision ids, nothing written) when an approver's valid verdict that differs from the file's cannot be written, so the earlier one would stand silently (a line a sync resolved, `via`, whose evidence is gone because it was reworded or its posting changed, or a rewrite that fails such as a line with an inline `<!-- -->`); an open line that is merely unposted or reworded is only skipped. It also refuses when no approvers are configured on the target branch, while the token identity holds the "Bypass rules on work item updates" permission or that cannot be read, when the comments were cut off (page limit or repeated page token) or an answer is not the expected shape (`truncated`, `CommentsUnreadable`), and on a decisions file that is missing, a symlink, outside the working tree, over 1 MiB, malformed (a line that breaks the grammar, an unclosed fence or comment) or has a repeated `D<n>`. With `approvers` configured, `ado decisions <id> --resolve` is **refused** (exit 2) with a text that names `--sync`: the approval path is comments then. A decision a sync answers that a standing superseder masks prints the same notice as `--resolve`. An existing line whose `why` or note contains the text ` · via:` is now malformed (`via` is a key; it fails closed: reword it). Residuals: a verdict already in the file is not withdrawn when its decision is later reworded (the done-time cross-check of a later task flags it); a `via` is a claim in a file a pull request controls, only the cross-check re-reads the comment; each decision with a valid command costs one read of the story's revisions (the `forged` check); the sync trusts the same local `origin/HEAD` as the other verbs.

**Approval flow for questions: `ado questions <id> --sync`.** With `approvers` on the target branch, the PO or another approver answers an open question in the story's comments: `/answer Q2: en-GB only` as the first non-empty line (the grammar and the guards above; an answer is cut to 500 characters). Anyone (the agent included) then runs `ado questions <id> --sync`, which writes `- [x] Q2: <question> → en-GB only (PO comment <comment id>) · owner: PO` into the ledger. It is a **local write only**: it reads the comments and the version history of the kit's questions comment (GET) and changes no ADO state, so it has no preview and no gate; only the answered lines change (line endings included), and the write is atomic and read back. An answer counts only when (1) the question is open and its line holds no answer text yet (`has-answer`: an unticked line with text a person wrote is never overwritten; a question that already has an answer is never replaced either, so a later `/answer` does not change it: edit the line by hand in a reviewed commit); (2) its current line was shown by the kit's questions comment (`not-posted`) and is not cut at 500 characters (`posting-lossy`); (3) the newest valid command for that question is newer than the version of that comment in which the line started to be shown (`older-than-posting`: an answer given before the question was posted, or before it was reworded, does not count; created time then comment id, a tie loses), and (4) its comment id is a plain decimal id (`bad-comment-id`); no valid command is `no-answer`. The text is scrubbed again (`→`, `->`, `·` and `|` become `-`, markup, fences and control characters are removed, the words `PO comment` are neutralised so only the sync writes that marker, an answer starting `assumed` gets the prefix `PO answer: ` so it never reads as the team's assumption) and capped at 500 characters.

*Question age.* A question's age is read ONLY from the versions endpoint (`api-version=7.1-preview.1`, the `modifiedDate` of a version is when the server wrote it) of the newest `[spec-kit-ado:questions]` comment written by the token identity: it is the `modified` of the first version of the unbroken run of versions, ending at the current one, that contain the question's whole rendered line (`Q2: <question>`, HTML-unescaped, the whole line: a version with `Q2:` and other text is not the question). A question whose line was reworded in the comment starts again at the version that holds the new words, and one that was changed and changed back restarts at the change back (a stricter reading than "the earliest version that contains it": the PO may not have seen the line in between); a no-op edit does not restart it. A version with any markup but `<br>` around the line (a line hidden in a style or a tag), one that does not start with the marker, or one over 256 KiB does not count. Nothing about the age is stored in the ledger (there is no `asked:` fallback) because the ledger is what a pull request controls. When the age cannot be established the sync refuses (exit 2, nothing written, the reason is a fixed key: `no-identity`, `no-comment`, `edited-by-other` (the comment was last modified by another identity), `versions-unavailable` (404), `versions-shape` (not versions 1..n matching the comment) or `date-shape`); an HTTP error other than 404 is exit 1. No request is made when no open question needs an age.

*Due questions.* With `unattended.assume_after_hours` set (1 to 720, target branch only), the questions still open after the sync whose age is at least that many hours are listed under `due`. "Now" is `client.server_now()`: the HTTP `Date` header of the newest ADO response plus the monotonic seconds since it arrived; the local clock (`time.time`, `datetime.now`) is never read, so setting it back or forward changes nothing. With `assume_after_hours` set and no usable server time (no `Date`, an unparsable one, a failed request) the sync refuses (exit 2, fixed text) rather than guess; without `assume_after_hours` nothing is ever due and no clock is needed. **The sync never closes a due question and a timeout never validates anything:** only `plan --close-assumed` (a later task) writes `assumed:` plus an OPEN `D<n> kind: assumption` that must be posted and approved.

The output (JSON) lists `answered`, `open`, `due` and `ignored` (question ids), `skipped` (id → rule: `has-answer`, `posting-lossy`, `not-posted`, `no-answer`, `older-than-posting`, `bad-comment-id`) and `bad_newer`, the count of later malformed command lines by an approver for each checked question (fixed text, a number only, plus a `notice` line: `/answer Q3 oops` may be an answer typed wrong, so read the thread when it is not 0); never the text of a question or an answer. It **refuses** (exit 2, a fixed text naming only ids, nothing written) with no approvers on the target branch, while the token identity holds the "Bypass rules on work item updates" permission or that cannot be read, when the comments were cut off or are not the expected shape (`truncated`, `CommentsUnreadable`), when the token identity is unknown or anonymous, on a ledger that is missing, a symlink, outside the working tree, over 1 MiB or malformed (no section 2, an unclosed fence or comment, a repeated or non-ASCII `Q<n>` id, a question line over 2000 characters), and when an approver's valid answer cannot be written (an inline `<!-- -->` on the line, a result over 2000 characters): the question would otherwise be taken as unanswered. Residuals: an answer already in the ledger is not re-checked here, and a hand-written answer (or a hand-written `(PO comment <id>)`) is an accepted residual, a claim in a file a pull request controls and reviews (the design does not cross-check ledger answers); a newer valid `/answer` on an already answered question is never applied but is listed under `ignored` with a notice (`answered already: a later /answer was not applied; correct the ledger by hand`), unless the line already names that very comment; the kit's own comment is written by the agent's identity, so it can post, edit or repost the questions at will: that can only restart or delay an age or make an answer older than its posting, never make a question older than the server's clock allows; a line the agent hid in markup is not counted, but ADO's own wrapping of a comment's text is not verified (a wrapped comment would fail closed as `not-posted`); `due` questions are only a list until a human or `plan --close-assumed` acts.

**Finding an approver's identity id.** `approvers` takes identity GUIDs, never names or e-mail addresses. Ask the approver to comment once on any story, then run `ado comments <story id> --author-ids`: it prints one line per comment, `date | author id | first 40 scrubbed characters`, to the terminal only (it writes no file, not even under `.ado/`, and cannot be combined with `--out`). Copy the GUID of the line you recognise by its snippet, then **verify it against that person's user page in ADO** before you put it in `approvers`: a snippet can be spoofed, since the agent can post a comment that reads like the approver's (the token identity is still excluded from approving by `ado doctor` and the excluded set, but another identity's look-alike text is not detected by this listing). The id is checked against the GUID pattern (else `?`) and lowercased. No identity display name, unique name or e-mail address is printed, but the snippet is the comment's own text: a name typed into a comment shows as typed, because only ANSI and control characters, `@mentions` and e-mail addresses are removed from it. A malformed answer from ADO (a repeated or missing comment id, an unexpected page shape) prints `error: comments unreadable (<reason>)` and exits 1. If a `note:` line on stderr says that not every comment was read, the story has more comments than the page limit allows and an older commenter may be missing from the list. The ids that can never count as approvers (comment-reading code, used by the later verbs of this version) are the token identity plus the author of every comment that starts with a `[spec-kit-ado:` marker, anonymous never included.

**Recommended setup** (identity binding protects against the agent, not against anyone who holds an approver's credentials):

- The agent never runs as an admin or an approver. It runs as a **Contributor without the "Bypass rules on work item updates" permission**,
  with that identity's PAT.
- Approvers are **separate human identities**: a separate account or browser profile, and no approver PAT in the agent's environment. If your
  own PAT runs the agent, you cannot be its approver: you need a second identity.
- The CI service identity is never an approver.
- `ado doctor` fails when an approver is the identity of the token it runs with, and, when approvers are configured and nothing fails, shows this reminder in the fix text of the `approvers` row (text and JSON). The reminder
  sits on the `ok` row on purpose: a `warn` row would not change the exit code either (only `fail` does), and it would be a warning that never goes away.

**Residuals (stated, not closed).** Deleting `origin/HEAD`, or rewriting `refs/remotes/origin/<base>` locally, changes what the local CLI trusts
(CI fetches fresh, so it is not affected). Other verbs' `--base` still accepts revision expressions (`main@{1}`) through `strict._resolve_base`, so a
local run of those can be pointed at an older target config; CI is not affected, and `config.trusted` refuses such a base. Anyone who holds an approver's credentials, the bypass-rules permission or admin rights on the
repository is outside this protection, and so is raw REST with the PAT. This is process enforcement plus identity-bound approvals where you
turn them on, not a security boundary.

## `gate`

```json
"gate": {
  "tests": { "**/*.spec.rb": "\\bexpect\\(" },
  "block": ["ac_traceability"]
}
```

- `tests` maps a test-file glob to a regex that counts as an assertion. Your entries are
  added to the built-in set (Python, JS/TS, Java/Kotlin, C#, Go, Apex), and an entry with
  the same glob replaces the built-in one. Files matching any glob are where the gate
  looks for the test IDs named in ledger section 3.
  The gate reads only regular files of at most 1 MiB that really live under `--src`: it never follows a symlink (not even one pointing inside the repo), and it skips FIFOs, devices and larger files. Because the PR supplies both the files and these regexes, reading through a symlink would let a PR probe files outside the repo one bit at a time. The ledger `ado gate` reads must meet the same rules (else it is reported unreadable). Skipped files are counted in the summary (`N file(s) skipped: ...`), never named.
  Each glob must be 1 to 200 characters with every `[...]` class closed and valid, and each regex 1 to 500 characters and compilable; otherwise it is a config error (exit 3 for `ado gate`) that names the entry by position (`entry #2`), never by its text, because the config comes from the PR and the message reaches the CI log.
- `block` lists the checks that may fail the gate (exit 1, and a failed CI check). Valid names are exactly the eight below; any other entry is a config error (exit 2; exit 3 and a red CI check for `ado gate`), so a typo such as `open_question` cannot silently switch a check off:
  - `ac_traceability` — an AC row in section 3 has no test (an empty or placeholder
    tests cell) or names only tests that cannot be found under `--src`. The AC are counted
    from the `### Acceptance Criteria` lines in ledger section 1 (AC-1 is the first line): every AC line in
    section 1 without a row in section 3 is unmapped, so a ledger whose section 3 is empty or still holds the
    placeholder row blocks when `ac_traceability` is listed here. Only a ledger with no AC lines
    and no AC rows is reported as not evaluated, and that never blocks.
  - `assertion` — a changed test file has no assertion match.
  - `ac_drift` — the story's acceptance criteria changed since the ledger was seeded.
  - `open_questions` — ledger section 2 still has an open question (`- [ ] Q<n>: <question> → _(open)_ · owner: <role>`; open means an unticked box or an `_(open)_` answer). Always reported as `open_questions` in the gate output; it fails the gate only when listed here.

  - `commits_without_story` — a non-merge commit in `<base>..HEAD` (`ado gate --base REF`, which the CI templates set to `origin/<target branch>`; without it, the branch `origin/HEAD` points at) whose message lacks this story's `AB#<id>` (word-bounded: `xAB#2` does not count, nor does another story's `AB#3`). Always reported as `commits_without_story` (short SHAs); when the base cannot be resolved (`--base` ref not found or starting with `-`, no `origin/HEAD`) or git fails, `commits_note` says the commits were not checked and the gate does not block. Fails the gate only when listed here.

  - `open_decisions` — the story's decisions file `<dod_path>/Decisions_<id>.md` (not the ledger) still has a `D<n>` line that is open or `rejected`; a `validated` one is resolved. Reported as `open_decisions` (ids in numeric order) **only when that file has at least one `D<n>` line**, so a repo without a decisions file keeps the v0.2 output exactly. A `D<n>` line that breaks the grammar, an unclosed fence or comment in the file, or a file that exists but cannot be read (a symlink, outside `--src`, over 1 MiB, not UTF-8) adds `?` to the list, which blocks when listed. Fails the gate only when listed here.

  - `rule_coverage` — business rules (`rules.enabled`): a rule that binds the story is cited by no AC row with a found test, a cited id is unknown, a rule is not confirmed yet (`unconfirmed`) or changed against `Rules reviewed:` (`changed`), a rules file has an error problem, is missing or has another format, or the ledger header lines are absent or malformed. Reported as the `rules` key (and one `Business rules` line in the summary) **only when `rules.enabled` is true**; with `rules` absent or disabled the output is unchanged. It is local: the ledger and rules files on disk (your working tree locally, the checkout in CI), no request. In strict mode with `rules.enabled` it is part of the floor (like `ac_traceability`); in advisory mode it blocks only when listed here. Details: [business-rules-reference.md](business-rules-reference.md#the-gate-check).

  - `rule_drift` — business rules (`rules.enabled`), online: the committed rules files differ from the rules live in ADO (a rule of the story's live scope is missing or edited in its file, `Rules from:` is not the live chain, the file's Problems lines differ), or the live rules could not be read (`rules-unreachable`: ADO down, or the gate's token needs Work Items: Read on the Epic/Feature's project; shown as `?`), or `--offline` skipped the check. Reported in the `rules` key (`drift`, `unreachable`, `drift_note`) and one `Rule drift` summary line **only when `rules.enabled` is true**. In strict mode with `rules.enabled` it is part of the floor, so `ado gate --offline` is then a finding; in advisory mode it blocks only when listed here. Details: [business-rules-reference.md](business-rules-reference.md#drift).

  Missing evidence (a `green` row without a commit or PR) is always a warning only.

  Drift is reported as **not evaluated** (`drift.evaluated: false`, with a `note`) whenever it cannot be compared: `--offline`, no token or ADO unreachable, or a ledger with no AC hash. That is never the same as "no drift", and it never blocks, even with `ac_drift` in `block`.

With `block` empty the gate is advisory: it reports and exits 0. Missing information
never fails it: no ledger, an unreadable ledger, or ADO being unreachable or the token missing (drift is then
not evaluated, with a note that says why) each produce a note and exit 0. Test files that match no glob are not
scanned for assertions; add a `tests` entry for your language to cover them.

## Checking your setup

`ado doctor` prints one row per check, each `ok`, `warn`, `fail` or `unknown` with a fix; `ado doctor --json` prints
`{"rows": [{"id", "status", "fix"}], "scopes": {}}` (the row ids are stable). It exits `0` when no row fails and `1` otherwise. It writes nothing,
and its only network call is one GET of `connectionData` through the normal client, with a single attempt (no retry) and a 10 second timeout. `unknown` means a check could not tell (for example
no network or no `origin/HEAD`); it is never shown as `ok`. Row texts are fixed: ids, counts and version numbers only, never a token, a name,
an email or a config value (a config error names the key by position).

| Row | `ok` when | Otherwise |
|---|---|---|
| `git` | git 2.24 or newer | `fail` if older or missing |
| `specify` | `specify --version` is at least `>=0.9.0` and at least `requires.speckit_version` of the installed `.specify/extensions/ado/extension.yml` (a checkout can raise the floor, never lower it) | `warn` if not installed, `fail` if older |
| `shallow` | the clone is complete | `fail`: run `git fetch --unshallow` |
| `config` | `ado.config.json` validates | `fail`, naming the key |
| `config-target` | the target branch's (`origin/HEAD`) `ado.config.json` validates | `fail` if unreadable or invalid, `warn` if absent, `unknown` without `origin/HEAD` |
| `token`, `identity` | a token is found and ADO accepts it as a real user | `fail` with no token, a rejected token, an anonymous `connectionData`, or a 404 (check `organization`); `unknown` when ADO cannot be reached or does not say who you are. `connectionData` is organization-level and does not check the project: a wrong project still shows `ok` here, and only the scope probes (a later task) will catch it |
| `extension`, `workflow` | the installed version (`.specify/extensions/ado/extension.yml`, `.specify/workflows/ado-lifecycle/workflow.yml`) equals the CLI's | `fail` on a mismatch, `warn` if not installed |
| `approvers` | the target branch has no approvers and is not in comment mode, or none of its approvers is the token's identity | `fail` if an approver is the identity of this token, or if the target branch sets `"approval": "comment"` and lists no approvers (nobody can approve); `unknown` when the target branch cannot be read (unless the working-tree config has neither key) or the token identity is unknown. With approvers configured and no failure the row is `ok` and carries the one-human reminder below. Doctor compares with the local token identity only: the CI token identity and the authors of `[spec-kit-ado:*]` comments need a story's comments, which doctor does not read yet |
| `stack`, `kits` | `ado stack show` says approved with no note; `ado kits verify` has no finding | `warn` in advisory mode, `fail` in strict (no profile at all reads "no stack profile yet (optional): run `ado stack detect`" in advisory mode) |

`git` and `specify` run with a scrubbed environment (no token), a timeout and no input; only a version number is kept from their output.
`--probe-item ID` is accepted and ignored for now: it belongs to the scope probes, which are not part of this build. Doctor is a help, not a
security boundary: a hostile checkout shapes the local rows it can read.

## Credentials

The token is not part of this file. The CLI looks for it in this order:

1. `$ADO_TOKEN` (CI sets this; in Azure Pipelines from `$(System.AccessToken)`).
2. The store `ado setup` wrote to: the macOS Keychain, or `~/.azdo/<org>.token` (mode
   0600) on Linux and as the macOS fallback. On Windows it is the same plaintext file
   under your user profile; mode 0600 has no effect there, so only the profile's access
   control protects it.

A personal token needs **Work Items: Read & Write**, and **Project and Team: Read** for `ado setup` and `ado branch --link`, which read the project record (Microsoft documents that call as needing it; not tested with a token limited to exactly these scopes). With `repo_host: azure`, opening or
commenting on PRs through `ado pr` also needs **Code: Read & Write** (a token allowed to write to Azure Repos), and
`ado branch <id> --link` (the branch in the story's Development section) needs **Code: Read**
(it looks up the repository id) and **Project and Team: Read**; a 401/403 from either means that scope is missing. On GitHub, PRs go
through `gh`, so no Code scope is needed.

## Exit codes

`0` success; `1` an ADO/HTTP error, a failed item in a batch, a blocking gate, or a DoD
checklist that is not ready (`ado branch --id-from` also exits 1 when the branch names no story); `2` a config, credential or
argument problem, or a plan that changed since approval (`--expect-plan`); `3` only for `ado gate`,
`ado branch --id-from` and `ado strict mode`: `ado.config.json` is present but invalid (CI fails on it). The `ado stack` and `ado kits` verbs use only `0` (success, or a preview) and `2` (a refusal, an invalid profile or lockfile, a missing terminal for `--apply`, a usage error); `ado stack show --check` and `ado kits verify` also exit `2` on a finding (in advisory mode `--check` always exits `0`).

## Where a story is

`ado status <id>` answers "what do I do next?" with the first stage a story has not met and one command: `Story 1001: tasks-ticked. Next: speckit.ado.implement 1001`
(`Why:` adds a fixed sentence; `--json` prints `{stage, next, why, board_checked, run, run_notes, not_checked, board}`, and `catch_up` with `--catch-up`). It writes nothing and prints stage ids, counts and the
story id only: never ledger, spec, decision, comment or ADO text. It exits `0` whatever the stage and `2` for a usage error.

| Stage | Met when | Needs ADO |
|---|---|---|
| `config` | `ado.config.json` is valid | no |
| `ledger` | `<dod_path>/DoD_<id>.md` is a readable regular file inside the working tree with no unclosed fence or comment | no |
| `stack-profile` (strict) | `ado stack show --check` would exit 0 | no |
| `rules` (`rules.enabled`) | the rules files named by `Rules from:` are present and every in-scope rule is confirmed in `Rules reviewed:`. Local only: the live `rule_drift` check is in `ado gate`. An unconfirmed rule is free (the next command is yours to run); a changed one needs a human's own terminal, and the `why` says which | no |
| `questions-posted` | the open questions are posted as the one questions comment (or there is nothing to post) | comments |
| `questions-answered` | no open question is left in ledger section 2 | no |
| `plan`, `tasks` | `plan.md` exists, `tasks.md` lists tasks (in the ledger's spec dir) | no |
| `board-tasks` | every task of `tasks.md` has a Task under the story | child Tasks |
| `tasks-ticked` | every task of `tasks.md` is ticked | no |
| `board-sync` | no Task differs from `tasks.md` (what `ado push` would update) | child Tasks |
| `decisions-posted` | no decision line is unposted, and every `posted:` marker names a decisions comment that is on the story (a `posted:` marker is not an authorship check: it does not show who wrote the comment) | comments |
| `verified` (strict) | a current verification record | no |
| `gate`, `review` | a current gate result that is not blocking, and a current review that does not block (a blocker blocks even when `review_block_on` is empty). Once the work has landed on the default branch (see `merged`) they are not judged stale | no |
| `pr-link` | the story has an `ArtifactLink` relation to a pull request: Azure Repos `vstfs:///Git/PullRequestId/<project guid>%2f<repo guid>%2f<number>` or GitHub `vstfs:///GitHub/PullRequest/<repo guid>%2f<number>` (a GitHub commit or branch link is not a PR). GitHub PR links appear only when the Azure Boards GitHub app is authorised in the project | story |
| `merged` | the ledger as committed on the branch `origin/HEAD` points at holds this ledger's latest `### Review` (else `### Gate`) heading: the work has landed, however it was merged. Fetch first; a commit that only names the story does not count. Without `origin/HEAD` the next command is `git remote set-head origin --auto` | no |
| `done-state` | the story is in `done_state`; whether the ledger is attached is not judged (`ado done` attaches it, even to a story closed by hand) (in strict mode with a decision still open its next command is `ado decisions <id>`, because `ado done` refuses) | story |
| `decisions-closed` (strict) | no decision is open or rejected | no |

A board stage is never reported as met when ADO could not be read. With `--offline`, with no token, or after one failed request, the remaining board
stages are not tried: they are listed as `Board not checked` and skipped, so the answer is the first unmet stage that could be read. If everything
that could be read is met, the stage is `board not checked` and the next command is `ado status <id>` (offline) or `ado doctor` (an error); it is never
`done`. `board_checked` is false whenever the board was not read, even if the answer is a local stage. An unclosed code fence or comment in the ledger gets `ado dod <id> --refresh` only when it is in section 1 (a refresh splices from section 2); elsewhere the fix is by hand. A file that cannot be read (a symlink, outside the working tree, over 1 MiB, not UTF-8) leaves its stage unmet.

**Runs.** After the stage line, `ado status` reads the newest (by `updated_at`) `ado-lifecycle` run of the story from `.specify/workflows/runs/<run-id>/state.json` and prints a fixed `Run <run-id>: ...` line:

| Run status | Line |
|---|---|
| `paused` | at a gate: answer it in a terminal; then `specify workflow resume <run-id>` |
| `failed` | the failed step and `specify workflow resume <run-id>` (it re-runs that step and everything after it) |
| `running` | over 1 hour since `updated_at` by the **server's** time: "the run may have been killed: resume refuses a running run", with the documented manual fix (set `status` to `failed` in that `state.json`, then resume; the kit never edits Spec Kit's files). No client, `--offline` or no server time: the age is not judged and the line says so. The local clock is never used |
| `aborted` | resume refuses it: `ado status <id> --catch-up` |
| `completed` | `--catch-up` too, when the story is still at a stage before `pr-link` |
| `created` | "created, not started" |

The state file is untrusted data (the agent can edit it): the read is confined (no symlink, only below `.specify/workflows/runs/`, at most 1 MiB, run id `^[a-zA-Z0-9][a-zA-Z0-9_-]*$`, no path built from file text); only the six Spec Kit statuses and the step ids of the shipped `ado-lifecycle` workflow are accepted (a built-in list pinned by a test against `workflows/ado-lifecycle/workflow.yml`, not the installed copy the agent could edit; a loop step is `<loop>:<step>:<n>` with both ids in the list and `n` digits); `output`, `error`, `execution` and every other field are never read or printed; the commands are fixed templates (story id and run id only). A run file tied to the story with an unknown status, a missing key or an unknown step gives "not readable by this ado version; use specify workflow status"; an oversized, symlinked or unparsable file is ignored and counted in one line (`Run: N run file(s) ignored ...`); with more than 2000 run directories the rest is reported as `older runs not examined`, not as unreadable.

`--catch-up` prints, in the order the workflow runs its steps (implement, decisions, verify, sync, gate, review, PR), the fixed-template commands for the stages that are **not** met. A local stage that is met lists nothing: its file (`plan.md`, a ticked `tasks.md`, the gate and review results) is the evidence, and `speckit.ado.plan` or `speckit.ado.implement` would regenerate it. A board stage that is unmet, or could not be read, lists only its preview and apply (`ado questions`, `ado push`, `ado decisions`: a preview with `--plan-out`, your yes, then the apply with `--expect-plan`); an unread `pr-link` lists nothing, because the PR may exist. Offline (or after a read error) with every local stage met the answer is "local stages are all met; board stages not checked: run `ado status <id>` online". Strict-only steps (`ado strict verify`) appear in strict mode only. The list ends with "run `ado status <id>` again after each step": the plan-questions round that `plan` can raise and the `wait-po-answers` gate are not modelled, so the list is the part of the recovery your story still needs, not a replay of the workflow. This is process help, not a security boundary: the ledger, the spec dir and the decisions
file come from the branch and can be edited.
